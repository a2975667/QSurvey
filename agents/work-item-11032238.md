Complete Fix: QV Navigator End-State, Snapshot Consistency, and Hydration
ID: 11032238
Owner: FE/State Team
Last Updated: 2025-11-04

Problem Statement
- After submitting the final QV question in a multi-question QV module, `qvNavigator.activeQuestionId` remains set (typically to the last question), despite all questions being completed. This is confusing in pure-QV flows and leaks into resume/hydration when the server snapshot is built from a pre-completion navigator state.

Observed Root Causes
- Final-submit path marks the question complete but does not clear or advance `activeQuestionId` when it is the last item in `order`.
- Reducers do not define an "all-complete" terminal state; `activeQuestionId` is always a valid ID whenever `order.length > 0`.
- Submission builds the `navigator` snapshot from the pre-completion state, so the server snapshot may be stale (missing the just-completed question and possibly pointing active to the last/next-incomplete).
- Hydration logic, when given a partial/older navigator, selects the first incomplete or (worse) fallback to the first question, never representing an "all-complete" state.

Goals (Definition of Done)
- When all QV questions in `qvNavigator.order` are marked completed, navigator reflects a terminal state: `activeQuestionId` cleared (null/undefined), and `completed` accurately set for all.
- Submission snapshot consistency: the `navigator` attached to request payloads reflects the post-submit state (i.e., includes the just-completed question and cleared active when appropriate).
- Hydration correctness: when the incoming snapshot indicates all items are completed (or the reducer can infer it), navigator ends in the terminal state (no active).
- Integration tests cover: QV-only surveys (2+ QV questions), mixed-module surveys (QV then non-QV), and resume flows with complete/incomplete snapshots.

Non-Goals
- Do not change server DTO surface areas beyond existing optional fields; continue omitting `activeQuestionId` when absent/null.
- Do not implement new UX; keep current navigation labels and flows unchanged aside from correctness.

Proposed Design
1) Terminal Navigator Semantics
   - Define that when every questionId in `qvNavigator.order` is completed, `activeQuestionId` becomes `null` (or `undefined`), representing "no active question".
   - Reducer helpers compute this terminal state on any navigator mutation (sync, explicit set, next/prev) to avoid drift.

2) Submission Snapshot Consistency
   - submitQvQuestion should construct the navigator snapshot for the outgoing payload based on the post-submit state:
     - Compute a next-state navigator where the current question is marked complete and `activeQuestionId` is either advanced (if there is a next incomplete) or cleared.
     - Dispatch that navigator update to the store (source of truth) before sending the payload so UI and saved snapshot remain in sync.
     - Build `navigator` for the payload from this updated state (or directly from the computed next-state).

3) Hydration Safeguards
   - In `fetchSurveyResponseByUUID.fulfilled` (and any other hydration path), if the incoming navigator's `completed` covers `order` entirely:
     - Set `activeQuestionId` to `null`/`undefined` (terminal state), regardless of absent/invalid `activeQuestionId`.
   - If snapshot lacks `completed` but reducer can infer all are completed from local state, prefer terminal state over defaulting to the first item.

4) Page-Level Sync Adjustments
   - QuadraticSurveyPage effects that sync `activeQuestionId` should not force a non-null `activeQuestionId` when all are complete. Respect terminal state.
   - Ensure resume heuristics do not override terminal state once established.

Data Model and Backward Compatibility
- `QvNavigatorState` stays the same: `{ order: string[]; activeQuestionId?: string | null; completed: Record<string, boolean> }`.
- For network payloads, continue omitting `activeQuestionId` if none; servers treat it as optional already.
- Hydration handles both the presence of `null` (if server ever sends it) and omission gracefully.

Implementation Plan (Frontend)

Phase A — Reducer Semantics
- File: `client/src/features/unifiedResponsesSlice.ts`
  1. Add a small utility `computeTerminalActive(order, completed) => string | null | undefined` that returns `undefined` (or `null`) when all in `order` are completed; otherwise returns the first incomplete (or preserves a preferred if valid).
  2. Update reducers that set/derive active:
     - `syncQvNavigator`: after normalizing `order` and `completed`, compute `activeQuestionId` via `computeTerminalActive` with respect to the preferred candidate. If all completed, clear active.
     - `setActiveQvQuestion`: if the requested candidate is falsy and all completed, clear active; otherwise validate candidate.
     - `goToNextQvQuestion`/`goToPreviousQvQuestion`: after computing next/prev, if all completed, clear active; otherwise set to appropriate neighbor.
     - Marking completion/incompletion: after `markQvQuestionCompleted` and `markQvQuestionIncomplete`, recompute terminal state for `activeQuestionId`.
  3. Hydration handlers (`fetchSurveyResponseByUUID.fulfilled`, plus any others): when building `state.qvNavigator`, if `completed` covers all items in `order`, force terminal state for `activeQuestionId`.

Phase B — Submission Orchestration
- File: `client/src/components/QsNavBar/submission.ts`
  4. Compute a post-submit navigator snapshot before dispatching submission thunk:
     - For the `questionId` being submitted: create a copy of current `qvNavigator`, set completed[questionId] = true, and recompute active with the same reducer logic used in Phase A (shared helper or duplicated pure logic here).
     - Dispatch `syncQvNavigator` with the computed `order`, `completed`, and `activeQuestionId` to update store immediately.
     - Build the payload `navigator` snapshot from this next-state (omit `activeQuestionId` if terminal).
  5. Ensure QuadraticSurveyPage no longer does an additional state push that conflicts (it can still call `markQvQuestionCompleted` or we can remove that call in favor of the orchestrated `syncQvNavigator` within submission). Choose one path for single-source truth; prefer the orchestrated call in submission.

Phase C — Page-Level Sync
- File: `client/src/pages/survey/components/QuadraticSurveyPage.tsx`
  6. In the effect that builds `desiredActive`, allow terminal active (null/undefined) when all are complete; do not override with the first item.
  7. After submission of the last question, do not manually keep `activeQuestionId` set; rely on the store update performed in Phase B.

Backward Compatibility / Migration
- Server snapshots that omit `activeQuestionId` are already supported; terminal state will simply be represented by omission.
- Clients resuming from older snapshots that do not list `completed` will continue to use existing inference; no change.

Risks and Mitigations
- Risk: Changing active clearing could conflict with existing UI assumptions. Mitigation: page-level sync updated to respect terminal state; integration tests cover both QV-only and mixed flows.
- Risk: Snapshot timing change might affect analytics order. Mitigation: ensure telemetry aggregator hooks remain unchanged; add assertions that payload shape is as expected.
