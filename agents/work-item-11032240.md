Server: Enforce Per-Question Option IDs in Results (Write + Read Guards)
ID: 11032240
Owner: BE/Results Team
Status: New
Last Updated: 2025-11-04

Problem Statement
- Results for a selected question may include optionIds that belong to other questions. This happens when stored QuestionResponses contain votes for foreign optionIds; the aggregation faithfully surfaces them in meta.optionTotals and raw rows.

Root Cause
- Write path does not validate that each vote.optionId belongs to the question’s options before persisting.
- Read path (aggregation) scopes to questionId at the QuestionResponse level, but it unwinds all votes in responseContent without filtering to the current question’s option set.

Scope
- Server-side only (NestJS + MongoDB). No schema changes required.
- Applies to both:
  - Designer results: GET `api/v1/protected/surveys/:surveyId/results`
  - Submitter results: GET `api/v1/survey/responses/:uuid/results`

Proposed Fix
1) Write-time validation for QV responses (preferred canonical fix)
   - File: `server/src/response/user-response.service.ts`
   - Touch points (ensure all create/update paths enforce filtering):
     - `createSurveyAndQuestionResponse(...)` (around first create flow)
     - `CreateQuestionAndUpdateSurveyResponse(...)` (single add/update path)
     - `createBatchSurveyResponses(...)` (batch create path)
     - `updateQuestionResponse(...)` (explicit updates)
   - Approach:
     - Fetch the target question by `questionId` (use existing CoreService methods) and derive `allowedOptionIds` from `question.options[*].optionId` (for QV question types).
     - Filter `responseContent.votes` to `allowedOptionIds` before saving.
     - Optionally log and count filtered votes for observability (guardrails only in non-prod logs).
     - Do not apply to Likert/Text.

2) Read-time defensive filter in aggregations (belt and suspenders)
   - File: `server/src/surveys/surveys.service.ts`
   - Method: `getSurveyResults(...)`
   - After `$unwind: '$questionResponse.responseContent.votes'` in BOTH pipelines:
     - Totals pipeline (optionTotals): inject a `$match` ensuring `votes.optionId` ∈ allowedOptionIds for the selected question.
     - Raw pipeline: inject the same `$match` to exclude foreign rows.
   - Implementation options:
     - Pre-fetch allowedOptionIds in Node (Mongoose `findById(questionId)`) and splice into the pipelines as a literal array.
     - Or `$lookup` the question inside the pipeline, `$project` allowedOptionIds, then `$match` with `$expr`/`$in` (heavier, but self-contained).
   - Keep pagination semantics intact: `$match` MUST occur before `$sort`/`$limit` and cursor calculations.

3) Optional data hygiene (one-off)
   - Script to sanitize existing QuestionResponses by removing votes whose optionId is not part of that response’s question’s options.
   - Dry-run mode first; commit change behind a feature flag/CLI command.

Testing Plan
- Unit tests (server)
  - Add tests for vote normalization (write-time filter):
    - New: `server/src/response/__tests__/vote-normalization.optionFilter.spec.ts`
    - Create responses containing a mix of allowed/foreign optionIds → expect saved responseContent to include only allowed ones.
  - Update/extend: `server/src/surveys/surveys.service.results.spec.ts`
    - Ensure `getSurveyResults` excludes foreign optionIds in both meta.optionTotals and raw when the underlying data contains foreign votes.

- Integration tests (server)
  - Seed a survey with two QV questions and overlapping/non-overlapping option sets.
  - Write responses that (intentionally) include cross-question optionIds.
  - Assert the designer and submitter result endpoints return only options from the requested question.

Acceptance Criteria
- Creating/updating QV responses stores only votes whose optionIds exist in that question’s options.
- Designer results meta.optionTotals and raw contain only optionIds from the requested question’s option set.
- Submitter results show only optionIds from the selected question.
- Pagination and cursor logic unchanged; filtering happens before sort/limit.
- No regressions to other question types (Likert/Text) or endpoints.

Risks & Mitigations
- Risk: Additional read-time `$match` could slightly impact aggregation performance.
  - Mitigation: Pre-fetch allowedOptionIds in Node and inject as a literal array to keep the pipeline simple.
- Risk: Existing polluted data in QuestionResponses.
  - Mitigation: Write-time fix prevents new pollution; optional migration cleans existing.

Change List (anticipated)
- `server/src/response/user-response.service.ts`:
  - Add helper to fetch allowedOptionIds for a question.
  - Apply filtering in create/update paths (single + batch).
- `server/src/surveys/surveys.service.ts`:
  - Inject `$match` on `questionResponse.responseContent.votes.optionId` against allowedOptionIds in both totals and raw pipelines.
- Tests:
  - New unit test for normalization filter.
  - Extend results service tests to cover filtering.
- (Optional) Script for one-off data hygiene.
