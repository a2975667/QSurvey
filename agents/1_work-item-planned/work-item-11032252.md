Render Approval Questions for Respondents
ID: 11032252
Owner: Frontend
Status: Proposed
Last Updated: 2025-11-20

Problem Statement
- Approval questions are supported in the backend (type `approval`, options array, `randomizeOptions`), but respondents have no UI to answer them.

Expected Behavior / Shape
- Survey JSON for approval questions: `_id`, `type: "approval"`, `question`, `description?`, `options: [{ optionId, optionName, description? }]`, `randomizeOptions` (boolean).
- Respondent UI: reuse the QV voting layout for the voting phase, but the per-option dropdown should only offer a single choice: “Approve”. Selecting it marks that option as approved; leaving it unselected is equivalent to abstain.
- Submission shape: `{ responses: [{ questionId, responseContent: { approvals: ["<optionId>", ...], type: "approval" } }] }` (approval list contains only approved optionIds).

Tasks
- Add approval rendering in the respondent survey flow, preserving survey order (no QV-first reordering). For each approval option, show the option name/description and an “Approve” control (can be a dropdown with one item “Approve” or a checkbox aligned with the QV layout).
- Collect approved optionIds into `responseContent.approvals` when submitting; do not allow negative votes or limits.
- Respect `randomizeOptions`: if true and the backend sends randomized options, render in that order without additional sorting.
- Ensure mixed surveys (Text/QV/Likert/Approval) render and submit without conflicts.

Verification
- Manual: build a survey with Text → QV → Approval; as respondent, see all questions in order, approve selected options, submit, and confirm no errors.
- Automated: component/integration test that renders an approval question, toggles approval on one option, and asserts the submit payload contains `responseContent.approvals` with the selected optionId and `type: "approval"`.
