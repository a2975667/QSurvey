Fix Results Visualization Showing Options From Other Questions
ID: 11032239
Owner: FE/State Team
Status: Completed
Last Updated: 2025-11-04

Resolution Summary
- Root cause confirmed: the series builder appended optionIds found in raw rows even if they were not part of the current question’s `optionTotals`, and the page didn’t fully reset local state when switching questions. This produced cross-question options in the visualization.
- Implemented strict filtering in `buildOptionSeries` (default) and added a guarded legacy mode via an `includeOrphans` flag. Added state reset on question change and a defensive validation that fetched pages match the requested `questionId`.
- No backend changes were necessary; this is a client-side fix only.

Problem Statement
- In the designer Results dashboard, when viewing results for Question A (first QV question), the visualization sometimes includes options that belong to Question B (second QV question), even though the server data and totals shown for the current view correspond only to Question A.

Observed Symptoms
- Option cards/charts on the results page render entries whose `optionId` is not part of the selected question’s option universe.
- “Raw Votes (Debug)” may also contain rows that do not map to the current question’s options.

Likely Root Causes (Client-side)
1) Series builder includes “orphans” from raw rows
   - File: `src/components/results/utils.ts`
   - `buildOptionSeries()` intentionally adds any optionId found in `rawRows` even if it isn’t listed in `meta.optionTotals`:
     - Comment: “Include options that might not be present in meta.optionTotals but appear in raw rows.”
     - If rawRows contain stray optionIds (from another question or a backend pagination quirk), those become visible series.

2) State not fully reset when questionId changes (lower probability)
   - File: `src/pages/designer/SurveyResultsPage.tsx`
   - On `questionId` change, we refetch results, but we don’t explicitly clear `filteredIds`/`meta`/`rawRows` before the new fetch, which could show transient mixed state during render.

3) Backend pagination returns mixed rows (defensive guard)
   - If server returns raw rows that include optionIds outside the target `questionId`, the current UI will surface them because of (1).
   - Client should defensively filter raw rows to the allowed option set for the selected question.

Scope
- Fix should apply to the Designer results page and any submitter-facing results surfaces that use the same utilities.

Proposed Fix (Client)
1) Strict option filtering in series builder
   - Update `buildOptionSeries(optionTotals, rawRows)` to exclude optionIds that are not present in `optionTotals` by default.
   - Option A (simplest): filter `rawRows` by an `allowed` set: `const allowed = new Set(optionTotals.map(o => o.optionId))` and process only rows with `allowed.has(row.optionId)`.
   - Option B (configurable): add a third param `includeOrphans = false` (default), and only when true, retain the current “include extras” behavior for tools that need it.

2) Reset view state on question change
   - In `SurveyResultsPage`, before firing a new fetch when `questionId` changes, reset local state to avoid transient mixed data:
     - `setMeta(null); setRawRows([]); setFilteredIds([]); setNextCursor(null); setError(null)`.

3) Defensive metadata validation (optional but recommended)
   - After fetch, if `payload.meta?.questionId !== requestedQuestionId`, discard that page and surface an error (or retry) to prevent pollution by mismatched pages.

4) Reuse in submitter results (if affected)
   - `SubmittedResultsSection` uses the same visualization; ensure any raw rows passed into `buildOptionSeries` are filtered to the question’s options as above.

Testing Plan
Unit tests

  - Given `optionTotals` for Question A and `rawRows` with a mix of A and B optionIds, verify the output series only contains A optionIds by default.
  - If introducing `includeOrphans = true`, validate the previous behavior remains available and covered.

Integration tests
- Designer Results page (`src/pages/designer/__tests__/SurveyResultsPage.test.tsx` or a new test):
  - Mock API to return `meta.optionTotals` for Question A and `raw` that includes some rows with a foreign `optionId`.
  - Assert that the rendered visualization excludes foreign options.
  - Assert that changing `questionId` resets state and the visualization shows only the new question’s options.

Acceptance Criteria
- Viewing results for a question never shows options that do not belong to that question.
- Pagination and “Load more raw votes” do not introduce foreign options.
- Switching questions does not display transient data from the previous question.
- Existing results UI and charts remain functional; no regressions in totals and meta-summary counts.

Risks & Mitigations
- If any downstream consumer relied on “include orphans” behavior, making strict filtering default could hide data; mitigate by adding optional flag and keeping default strict for user-facing views.
- Backend may already guarantee per-question rows; the client filter is still a safe defense-in-depth.

Change List (actual)
- `src/components/results/utils.ts`: Added `includeOrphans` param (default false). Filters `rawRows` to optionIds present in `optionTotals` by default; legacy behavior available when `includeOrphans=true`.
- `src/pages/designer/SurveyResultsPage.tsx`: Resets `meta`/`rawRows`/`filteredIds`/`nextCursor`/`error` on `questionId` change to avoid mixed state; validates `payload.meta.questionId` matches request; otherwise surfaces an error.
- `src/pages/survey/components/SubmittedResultsSection.tsx`: No code changes required. It reuses `buildOptionSeries`, so filtering now applies automatically.
- Tests added:
  - `src/components/results/__tests__/utils.buildOptionSeries.test.ts`: unit tests for orphan filtering and opt-in legacy behavior.
  - `src/pages/designer/__tests__/SurveyResultsPage.test.tsx`: integration tests ensuring foreign optionIds are excluded and state resets when `questionId` changes.
