Multi-QV Navigation Design Notes
- Goals
  - Support surveys with N QV questions without reloading the page; allow forward/backward navigation with persisted state per question.
  - Maintain feature-flag parity: legacy `qsOptions` continues to mirror until unified path validated.
- Proposed state additions
  - `unifiedResponses.qvNavigator = { order: string[], activeQuestionId: string | null, completed: Set<string> }`.
  - Derive `order` from `questions.byId` sorted by `position`; hydrate once questions load.
  - `completed` toggles when user confirms votes (via `Next`); used for resume + progress UI.
- Actions/selectors
  - `setQvNavigator({ order, activeQuestionId })` fired when questions hydrate or resume occurs.
  - `goToNextQvQuestion()` / `goToPreviousQvQuestion()` compute index within `order`.
  - Selector `selectActiveQvQuestionId` drives `QuadraticSurveyPage`; fallback to first entry when unset.
  - Selector `selectQvProgress` summarises completed vs total for nav/status indicators.
- UI wiring
  - `QuadraticSurveyPage` iterates from navigator state instead of assuming `position === 0`.
  - Split into `QuadraticSurveyContainer` (navigator + chrome) and `QuadraticQuestionView` (single-question organizer/vote rendering) so per-question props stay isolated.
  - `QsNavBar` receives callbacks to advance/back using new actions; disable `Next` until invariants met (credits within total, required bins resolved).
  - When feature flag disabled, maintain legacy behaviour.
- Resume interplay
  - After hydration, compute `completed` from hydrated responses (non-zero votes or server-supplied markers) and set `activeQuestionId` to first incomplete.
  - Ensure nav honours skip confirmation per question even after resume.
- Test coverage
  - Reducer tests for navigator (order, active index, bounds when removing questions).
  - Integration test: mount page with two QV questions, simulate drag/drop + next/back, assert navigator updates and state isolation per question.

Key Invariants (must hold after every reducer)
- QV option appears in exactly one bin; positionsByGroup[group][i] === options[id].groupPosition.
- categoriesOrder and view categories dictate visual order; Skip placement depends on page (organize vs vote) and flags.
- Total spent ≤ totalCredits (with optional tolerance for rounding).
- question-scoped isolation: state for question A never mutates B.
- UUID is immutable on the client; only server acks/thunks set it. Updates reference surveyResponseId/questionResponseId.

State Contracts (unified slice)
- Per-question
  - QV: { options[optionId]: { group, groupPosition, votes }, positionsByGroup, categoriesOrder, bins: { hasUndecided, hasSkip, userDefined[] }, totalCredits, history(revision,lastAction,lastEventAt) }
  - Likert: { selection, optionName?, history(changes) }
  - Text: { text, history(length) }
- Session: { surveyId, surveyResponseId, uuid (read-only), questionResponseIds: { [questionId]: string }, status, error, submitQueue[] }

Permutations to Test (QV)
1) Drag within same bin (reorder)
   - For a bin of length n, test all i→j moves where i≠j; assert groupPosition recomputation and positionsByGroup equality.
2) Drag across bins (all pairs)
   - Undecided→Support/Against/Skip
   - Support↔Against
   - To/from Skip
   - To/from any user-defined category
   - Insert at top (j=0), middle, bottom (j=len)
3) Merge bins
   - For all distinct (source,target) in categoriesOrder, move entire source into target, assert:
     - positionsByGroup[target] ends with (or appropriately merges) source’s options
     - source is empty; all moved options’ group updated; positions recalculated
4) Split scenarios
   - Move subset back from target to a new/empty bin; verify invariants
5) Regroup + order strategies
   - Sort by votes desc; tiebreak by previous global position; asserts stable sort and recomputed positions
6) Toggle bin flags/page mode
   - hasUndecided=false removes Undecided from view categories
   - hasSkip=true: Skip at start (organize) vs end (vote)
   - userDefined categories reflected in view order and created if missing
7) Multiple QV questions
   - Perform operations on Q1; assert Q2 unchanged; repeat vice versa
8) Edge cases
   - Single bin only; moving into non-existent target (auto-create if allowed)
   - Empty bins; repeated merges; oscillating moves; large n (e.g., 100 options performance smoke)

Non-QV Scenarios
- Likert: successive selection changes; history change records; idempotent updates.
- Text: typing growth + backspace; history.length updates; long input boundaries.

Selectors to Validate
- selectQvGroupOptionIds(questionId, group): matches positionsByGroup.
- selectQvTotalSpent(questionId): sum(abs(votes)) with rounding behavior.
- Derived view categories based on (bins flags, page mode, userDefined list).

Submission Model
- After each question “Next”, submit the normalized per-question status only.
  - QV payload (minimal): { votes: [{ optionId, optionName, votes }…] }
  - Likert payload: { selection, optionName? }
  - Text payload: { text }
- Do not send positionsByGroup by default; keep for analytics if needed in metadata.
- On success, record/refresh questionResponseIds[questionId] and surveyResponseId; UUID remains unchanged.
- Ensure payload is stable (same snapshot ordering) for idempotence.
