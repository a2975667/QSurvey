## 2025-11-20 — Question Storage Design Drift
- Intended design: all question types (QV, Likert, Text, Approval, etc.) live in a single Mongo collection `questions`, distinguished by a `type` (or discriminator key). Business logic branches on `questionType`, similar to how `QuestionResponses` share one collection.
- Current implementation: each question subtype has its own Mongoose model. Although most schemas declare `collection: 'questions'`, any schema/controller change that omits this (or uses a different connection/model name) will create new collections (e.g., `likertquestions`, `textinputquestions`). When that happens, `CoreService.getQuestionsByManyIds` can’t find the documents because it queries the shared collection, leading to missing ID logs and empty question lists on surveys.
- Failure mode observed: creating a text question returned `_id ...c4b`, but the survey was updated with `_id ...c4d`, and `getQuestionsByManyIds` returned 0 docs. Causes to investigate: mismatched collections, controllers trusting client-provided IDs instead of the persisted `_id`, or UI using stale IDs.
- Guardrail plan: ensure every question model uses the shared collection/discriminator base, ensure create endpoints return and consumers store the persisted `_id`, and add integration tests that fail if any new collection for question subtypes appears or if survey-question linking doesn’t resolve through `getQuestionsByManyIds`.
